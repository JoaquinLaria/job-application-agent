1. Task and service

Offered. A job-posting eligibility screen (service offer, entry 232503), the screening step of the job-application agent I built in Homeworks 1 and 2. Given a posting and a synthetic profile it returns ELIGIBLE, STOP or UNCLEAR, each hard requirement with the exact sentence that states it, and any disqualifier. Before replying, code checks that every quote appears word for word in the posting and drops any that do not.

Delegated. The agent has two tasks, in order of preference. (1) Adversarial test cases for plain(), the real function my forum agent uses to turn Canvas HTML into text; a bug there breaks fingerprints, duplicate detection and read-back. (2) An independent check of 8 claims my screen makes about a fictional 10-line job posting, two of them deliberately false.

How it chose. No partner is hard-coded. On each discovery run the agent reads every service offer, and the model scores each one 0 to 10 against the task. Code adds a responsiveness signal (the provider's own replies in its thread, requests waiting over 12 hours) and excludes providers that have answered nobody while three or more requests wait; that removed a test-design offer (231986) that matched on paper but had 11 unanswered requests. A provider is hired only at a score of 6 or more.

2. Technical setup

  • Harness and model. A Python agent reusing my HW3 agent's Canvas client. Claude Sonnet through the MIT Parley gateway ranks offers, screens postings and, only as a fallback, reads values out of a reply. Acceptance is always decided by code.
  • Canvas. REST API with my own token from HW3, held in a GitHub Actions secret.
  • When it runs. GitHub Actions cron, twice an hour from 12 to 14 October (GitHub delays or skips some scheduled runs; a few cycles were started by hand). Each cycle: read the forum, answer requests in my offer thread, then advance the current hire.
  • Memory and replies without relay. state/hw4_memory.json, committed after every cycle, holds my offer id, handled requests, each hire (task, provider, request id, deadline, status, deliveries and check results), a pending-write record and a failure counter; hw4_runs.jsonl logs every cycle (28 so far). A hire moves from requested to checked, then accepted, one correction, or rejected; a decline or a missed deadline sends the agent to the next suitable provider (at most three, one at a time).

5. Safety controls

  • Credentials. Two Actions secrets, masked in logs, never written or posted. Outgoing text is blocked if it contains links, email addresses or key-shaped strings.
  • Untrusted peers. Peer text reaches the model only inside a <peer> wrapper with < escaped, as data. Peer code is never executed: values are read, not run. The model never decides acceptance.
  • Control line and write limit. Before every write the agent reads the HW4 description and writes only on COURSE-TEAM CONTROL: RUNNING. At most one write per cycle and three attempts per rolling hour, counting my HW3 agent's posts.
  • Verified, no duplicates. Intent is saved before each write and every post is read back by id. The first request's read-back failed because the fingerprint was taken from text that itself contained HTML examples. The post was on Canvas, so the next cycle adopted it as the request instead of resending (I added the request's details to memory by hand once, since the first version did not save them); the fingerprint now uses the HTML actually sent, and the pending record carries the full request.
  • Stops. Backoff on reads and model calls, never a blind retry of a write, a halt after three failed cycles in a row, and no action outside the run window.
